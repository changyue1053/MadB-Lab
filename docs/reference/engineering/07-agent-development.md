# MadB Agent 开发规范

适用于 MadB 与 MadB-Lab。目标是让每次改动对应既有任务、权威设计和真实验收，同时保留范围内的自主开发。使用现有文档、任务目录、检查命令和评审流程，不建立独立的 Agent 调度、任务协议或进度系统。

## 最小文件与实施责任

两个工程各维护一份简短的根 `AGENTS.md`，内容仅包含：本工程的规范入口、任务执行步骤、关键限制和实际验证命令。本文维护共同方法，根文件引用本文和对应工程规范，不复制整套架构与任务明细。只有某模块出现确有必要的差异规则时，才增加局部 `AGENTS.md`。

根文件应能从各自检出或固定版本的公开文档定位依据，不能依赖作者本机绝对路径、未登记的外部工作区或 Lab 对工具私有源码的依赖。使用的 Agent 在开工时必须实际读取入口及涉及模块的规则，不能假定写了文件就一定已加载。

根文件、真实命令入口和 CI 合入约束由 C01 落地；平台检查随对应工作包补齐。当前本文及计划表达实施要求，不表示规则文件、仓库权限或 CI 已部署。

## 权威来源与任务范围

| 内容 | 依据 | 执行要求 |
|---|---|---|
| 做什么、先后及何时完成 | [任务目录](https://github.com/changyue1053/MadB/blob/2c47c079dd08832a6ea2d82630cd249784fb6594/docs/catalog/implementation-plan.json)、[实施计划](../delivery/01-implementation-plan.md) | 绑定既有任务编号及本次范围；依赖按计划定义解释，提前探针不冒充整体验收 |
| 怎么实现与哪些边界不能改变 | 对应 architecture 规范、ADR、[工具骨架](https://github.com/changyue1053/MadB/blob/2c47c079dd08832a6ea2d82630cd249784fb6594/docs/architecture/02-modules-and-ports.md)和[Lab 骨架](../validation/02-lab-architecture.md) | 从任务的 documents 和适用 DEC 准入开始阅读，再追踪涉及的规范；无需每次通读全部资料 |
| 如何证明正确 | 任务 acceptance、适用 validation 文档、[质量门禁](05-review-and-quality-gates.md) | 按改动风险执行真实检查；部分成功不替代工作包验收 |
| 历史信息与视图 | reviews、研究案例、HTML | 仅作导航或指定快照的证据，不覆盖现行规范和任务状态 |

任务记录不能自行重定义架构或验收。文档与计划存在冲突、关键契约缺失或方案不可行时，说明具体位置、影响和最小调整方案；暂停依赖该决定的部分，可以继续无冲突的工作。已有明确授权的调整直接执行并同步相关依据，不重复请求确认；没有决定的实质变更交由对应负责人确定。

## 每次任务的四步流程

### 1. 对齐任务

在当前任务、Issue 或 PR 中记录以下四项即可，不另建任务卡文件或 schema：

```text
任务：既有编号 + 本次子范围
依据：相关规范、适用决定及当前文档/代码版本
范围：涉及模块或路径、明确不涉及的内容
验收：检查命令、预期结果及所需目标环境
```

先确认工作区已有改动和所需前提，保留他人的工作。尚未存在的命令写明由哪个既有工作包补齐，不能虚构通过结果。任务切换或上下文恢复时重新核对当前文件和任务记录；聊天摘要只帮助定位。

### 2. 在范围内实施

遵循[整洁代码](02-clean-code.md)、模块依赖和生成/手写分工，优先复用已有实现。内部命名、函数拆分、既定路线内的实现选择和针对性修复由 Agent 自主处理，不逐项审批。

改变已定技术路线、模块职责、依赖方向、工具链锁定方案、公开 API/ABI、所有权、线程或取消语义，需要先形成具体差异、兼容影响及验证方案，按现有决策流程确认并同步规范、计划，再实施依赖该决定的内容。不能把这类变化藏在普通重构中。范围外问题记录为后续事项；阻塞本任务时明确提出，不顺手扩大重构。

### 3. 按风险验证

使用质量门禁中已有的检查层次。文档修改执行相关文档检查；生成器修改检查重生成和真实消费；生命周期修改验证对应释放、取消与竞态。不强制所有任务全量构建、多 Agent 审查或新增测试；高风险原生与并发变更仍需独立审查。

记录命令、环境、对应代码或候选身份、结果及未执行项。检查后又修改相关内容，应重跑受影响部分；缺环境、超时、编译成功或 DOM 替身结果不能替代设备运行、完整消费或浏览器验证。

### 4. 对照验收交付

交付说明只需包含：实际改动、验证结果、未解决问题及本次完成范围。复核最终差异是否超出任务、违反规范或遗漏验收；必要评审和检查针对最终提交内容。

子范围完成不等于整个工作包完成。工作包状态仅在 catalog 维护，遵循既有 `implemented + passed + 有效证据` 条件；Agent 的文字总结不自动赋予验收、认证或发布资格。暂停或交接沿用当前任务记录，无需增加独立交接系统。

## 不得绕过的限制

- 不擅自扩大任务范围、改变既定契约或引入未经约定的替代技术路线；不以修改规范来掩盖未经确认的实现偏差。
- 不通过删测试、放宽断言、跳过必需项、修改 golden/expected 或降级门禁制造通过。确需修订预期或检查时，提供独立依据及差异，按现有评审流程处理。
- 不直接修补生成输出来代替修改生成源、模板或受管补丁；不把生成结果当作唯一正确性预期。
- 不覆盖他人的未提交工作，不擅自发布或执行破坏性操作。
- 不在功能任务中顺手削弱自身规则、CI 或验收条件；规则变更须明确列入已授权范围，并保留变更依据。
- 不虚报命令执行、平台能力或完成状态。历史报告保持原始内容，新结果单独记录。

规则文件提供执行依据；依赖检查、生成一致性检查、必需测试和合入设置约束可检查的违规，语义判断由对应审查承担。CI 工作流存在不代表必需检查已生效，C01 应实际验证失败不能放行；文件、凭证与发布权限沿用执行环境和仓库的权限控制，不能仅用提示词代替。

## 轻量化与计划接入

C01 交付两份根入口、可运行的首期检查及合入约束，复用一次真实小任务证明“按依据实施、按检查交付”。失败检查应阻断合入，未执行项不能计为通过；现有架构负例同时证明依赖限制有效，不另建 Agent 测试平台。

本规范适用于全部工作包，不批量复制到 41 份任务明细。新增能力仍按现有阶段完成；不增设 Agent 专属工作包、阶段、完成率或统一调度服务。自定义任务 schema、policy/checks JSON、目录级规则铺设、专门的证据与交接平台均不作为开工前置。

只有重复违规、稳定重复操作或真实协作冲突出现时，才为对应问题增加局部规则或小型检查。多人或多 Agent 并行时明确修改范围，共享契约先协调；最终验证集成结果，不把并行审查作为每项任务的固定成本。
